Code, data, hardware records and complete proofs for the research paper of the
same title. This repository is the data and code record cited in the paper's
"Data and code availability" section.

### Build the research paper

```text
cd iris_paper
python build_references.py          # writes references_iris.tex from ../references_db.tex
pdflatex iris_paper.tex             # run three times
```

It needs a TeX distribution with `lmodern`, `titlesec`, `tocloft`, `caption`
and `booktabs`. Every hardware number in the paper comes from
`hardware_macros.tex`, which `hardware/hardware_summary.py` generates from the
raw outputs (see "Hardware demonstrations" below).

## Build the PDFs

Use a TeX distribution with REVTeX 4.2 and the packages named in the preambles.
Run `bash build.sh` (or `build.ps1` in PowerShell). The build script runs

```text
python3 build_bibliography.py
pdflatex -interaction=nonstopmode -halt-on-error supplement.tex   (3 times)
pdflatex -interaction=nonstopmode -halt-on-error manuscript.tex   (3 times)
python3 finalize_pdf_links.py
```

Build the supplement first: the main manuscript imports its section references
through the standard `xr` package. No BibTeX run is required; rerun
`build_bibliography.py` whenever citations change. The last step needs PyMuPDF
and only produces the linked copies in `linked_pdfs/`.

## Redraw figures

`python make_publication_figures.py` regenerates 20 of the 27 figure files that the
two PDFs include (vector PDFs plus 600 dpi PNG previews) from the archived
CSVs, without rerunning Monte Carlo simulations. It needs matplotlib and a
LaTeX installation with the `lmodern` package, because LaTeX typesets the
figure text in the font of the documents. Each figure is drawn at its printed
width, so LaTeX includes it without rescaling.  `python make_junction_figure.py`
draws the junction and wall figure (`figures/junction_wall_geometry.pdf`)
from an instance generated by `layer_code_explicit.py`, and
`python make_scaling_figure.py` draws `figures/two_block_scaling.pdf` from the
scaling-campaign data in `numerical/scaling_campaign/`, and
`python make_intuition_figure.py` draws the schematic of main-text Fig. 3
(`figures/fault_distance_intuition.pdf`), which carries no data.
`python make_two_block_figure.py` draws main-text Fig. 5
(`figures/two_block_main.pdf`) from the scaling-campaign and
routed-campaign data, and `python make_hardware_figure.py` draws the three
hardware figures (see "Hardware demonstrations" below).  The former main-text
surface-code figure (`figures/revision_numerics.pdf`) is no longer included;
the same data appear in the supplement as `figures/threshold_G*d.pdf`.

The older helpers (`revision_figures.py`, `make_printscale_pass.py`,
`make_fragmentation_figure.py`, `make_ft_dependency_figure.py`,
`generate_figures.py`) are superseded for these files and are kept only as
research source; running them would overwrite the current figures with the
previous styling. Files in `figures/` that no document includes are earlier
artwork kept for reference.

## Reproducibility and data

`requirements.txt` and `environment-known-good.json` document the author's
numerical environment.  The revision scripts need the packages pinned in
`requirements-revision.txt` (`pip install -r requirements-revision.txt`), including
SciPy, ldpc and OR-Tools (the CP-SAT distance solver). `revision_environment.json` records the environment used
for this revision; it does not replace the simulation environment.

The primary continuous-transition dataset is
`numerical/continuous_transition/threshold_estimate/all_points.csv`:
255 parameter points and 4,534,000 shots, with 15 zero-noise controls. It is a
planar surface-code gauging campaign, not a layer-code simulation.
`numerical/stage_composed/` holds the earlier stage-composed controls, also on
surface codes. `measurement_interface_check.py` and its CSV support the
thin-versus-thick interface comparison (Supplemental Table S6).
`numerical/routed_campaign/` holds the routed nearest-neighbor two-block
campaign (certification, fault distances and minimum-weight witnesses; see its
`README.md`); `python routed_campaign_check.py` checks those tables and
witnesses, and `python band_spacelike_check.py` computes the spacelike limit
of the band input quoted with them.

The complete finite workflows are `run_verification.sh` and
`run_bridge_verification.sh`; they include additional work and may rerun
simulations. The deterministic checks rerun for this revision are

```text
python3 reproducibility_checks.py
python3 slab_interface_audit.py
python3 factory_map_audit.py
python3 measurement_interface_check.py
python3 frame_propagation_check.py
python3 distance_lower_bound_check.py
python3 glue_example_check.py
python3 boundary_composition_check.py
python3 resource_defect_check.py
python3 resource_estimate.py
python3 rectangle_slice_check.py
python3 schedule_verifier.py
```

All pass.  The first five reproduce their archived outputs byte for byte;
the next five check the revised distance theorem, boundary interface,
resource lemmas and resource estimate.  `rectangle_slice_check.py` (added
8 October 2026, needs OR-Tools, about 30 minutes on 8 cores) builds the
relative problem of a gauging rectangle from the phenomenological model and
checks by exact CP-SAT minimization that both CSS sectors attain the bound of
Supplemental Proposition "Slice bound for a gauging rectangle"; it writes
`rectangle_slice_check.csv`.  `schedule_verifier.py` (added 9 October 2026,
standard library only, under a minute) builds and exports a complete serial
schedule (`schedule_trace.json`) and checks the schedule invariants (I1)-(I3),
the lifecycle of every cell, the geometry, the factory slots, and the path
separations of Supplemental Lemmas "Paths between primitives" and
"Resource-boundary separation", with nine negative controls; it writes
`schedule_verifier_report.json`.  `factory_3d_routing.py` and
`factory_3d_routing_coords.csv` are an early schematic sketch: their
coordinates overlap by design and they are not a physical allocation.
`wb_exact_cell_patch_audit.py` is the archived certificate of an
earlier version and is kept for provenance only (supplement, Sec. "Archive").
Monte Carlo seeds are recorded integers; `REVISION_RUNS.md` lists every
command. Finite
tests do not independently establish the arbitrary-size theorems.

## Hardware demonstrations

The folder `hardware/` holds everything behind main-text Sec. VII and
Supplemental Sec. "Hardware demonstrations": runs on IQM Emerald (through
Open Quantum) and on IBM `ibm_fez` and `ibm_kingston`, made on 13 and
14 October 2026.  It contains the circuit definitions, the placement and
pre-submission checks, the circuits exactly as submitted (`qasm3_*.qasm`,
`*.qpy`), the raw platform outputs, job identifiers, IBM calibration
snapshots, Open Quantum backend descriptions, and the analysis scripts.  The
helpers in `hardware/submission/` submit and fetch jobs; they read access keys
from files that are not part of this package, so they cannot be run without
your own accounts.  Two Rigetti attempts are excluded from the analysis
(supplement, "Excluded runs"); their outputs are kept.

Every hardware number in the two PDFs is generated, not typed:

```text
python hardware/hardware_summary.py   # writes hardware_tables.tex, hardware_macros.tex
python make_hardware_figure.py        # writes figures/hardware_{overview,results,chips}.pdf
```

`hardware_overview` is main-text Fig. 6, `hardware_results` (every run) and
`hardware_chips` (every placement on the chips) are in the supplement.  The
chip coordinates are derived from the coupling maps in
`hardware/oq_backend_iqm_emerald.json` and
`hardware/ibm3_calibration_ibm_kingston.json`.

`hardware_summary.py` needs NumPy, Qiskit, Stim and OR-Tools (it imports the
analysis modules); the figure needs matplotlib and LaTeX as above.  The
pre-submission checks (`final_check_iqm.py`, `export_multiplicity.py`,
`export_rounds.py`, `ibm_rounds_plan.py`, `ibm3_reset_plan.py`) also need
Qiskit Aer and rustworkx, and the IBM planning scripts need an IBM Quantum
account for the backend description.
